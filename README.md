# Тесты выбора бонусного пакета для пополнения

Проект проверяет `PUT /api/v1/bonus/packets/refill`: авторизацию, обязательные
поля, ID пакета и статусы пополнения. Интеграционные сценарии используют
регистрацию через API, SSH-команду `simulate:refill:greenback` и MySQL.

## Установка

Используйте Python 3.13 (эта версия также настроена в CI):

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

## Локальные проверки без стенда

```bash
python -m pytest -m "not integration" -q
```

Эти тесты блокируют внешние HTTP/SSH/MySQL-вызовы. Они проверяют зависимости
всех интеграционных тестов, создание пополнений и их владельцев, статусы,
таймауты, SSH-команды, видимость изменений БД и достоверность проверок бонусов.
SQLite используется как локальная модель; результаты не заменяют прогон API.
GitHub Actions запускает этот набор при push и pull request.

Отдельная проверка подготовки интеграционных сценариев без выполнения фикстур:

```bash
python -m pytest --setup-plan -q tests/bonus_packets
```

`--collect-only` лишь перечисляет тесты и не обнаруживает все ошибки фикстур.

## Подготовка стенда

```bash
cp .env.example .env
```

Заполните значения в `.env`:

| Переменная | Назначение |
| --- | --- |
| `DEV_STAND` | Имя стенда; API находится на `https://<DEV_STAND>.dev-mst.com` |
| `SSH_HOST` | Суффикс хоста SSH; итоговый адрес `<DEV_STAND>.<SSH_HOST>` |
| `SSH_USER` | Пользователь SSH и, в текущем клиенте, пользователь MySQL |
| `HOST`, `PORT` | Адрес и явный порт MySQL |
| `PASSWORD`, `DATABASE` | Пароль и имя БД |

Для SSH должен быть настроен ключ/agent и доступ к `sudo -iu mostbet`.
Необходимы права на чтение тестовых таблиц и изменение статуса пополнения.
Реальные пароли и токены остаются в локальном `.env`, который исключён из Git.

На стенде должен быть доступен обычный бонусный пакет для MOSTBET-сценария
и поддерживаться специальные значения MWL `50000` и `50001`. Фикстура выбирает
существующий обычный пакет по ID, но не может определить его бизнес-пригодность
без правил стенда. Для отрицательного сценария выбирается отсутствующий ID
в диапазоне `49000–49999`; если весь диапазон занят, подготовка явно завершится
ошибкой. `username` регистрационного API должен соответствовать `refill.user_id`,
как предполагают текущие консольная команда и схема проекта.

## Интеграционный прогон

```bash
python -m pytest -m integration -q
python -m pytest -m integration -q tests/bonus_packets/api_v1_bonus_packets_refill/test_field_refill_id.py
```

Полный запуск обоих наборов: `python -m pytest -q`.

Интеграционные тесты создают пользователей и тестовые пополнения, изменяют
статус пополнения и выбранный пакет. Запускайте их на выделенном тестовом
стенде. Автоматическое удаление созданных сущностей не реализовано: используйте
согласованный сброс тестового стенда или его штатную процедуру очистки.

## Фикстуры и изоляция

- `create_user` возвращает `User` с `username`, `password` и `jwt_header`.
- `create_user_and_refill(status)` возвращает `(user, refill_id)`. Каждый вызов
  создаёт своего пользователя и выставляет любой из статусов `0`, `1`, `2`, `3`,
  включая `2`. Для авторизации используется `user.jwt_header` из той же пары.
- DB/SSH-клиенты создаются только при вызове фабрики. Отрицательные случаи,
  которым не нужно пополнение, используют только `create_user`.
- Появление записи после SSH ожидается ограниченно; ошибка подготовки содержит
  имя пользователя. Таймаут ожидания не включает время выполнения самого SQL.
- Клиент MySQL использует `autocommit=True`: независимые SELECT видят уже
  зафиксированные изменения API/SSH и не сохраняют снимок предыдущего теста.
  Это клиент отдельных операций, а не интерфейс составных транзакций.
- Проверки ошибок сравнивают связанные данные до и после запроса. Для MWL
  проверяется отсутствие изменений опций, в том числе с другим `packetId`.

Перезапуск упавшего теста не скрывает ошибку: автоматические повторы запросов
регистрации и пополнения не включены.
