# API-автотесты

Проект для автоматизированной проверки API: авторизации, валидации запросов,
бизнес-сценариев и изменений данных в MySQL. Тесты организованы по функциональным
областям; по мере развития проекта сюда будут добавляться новые API и сценарии.

Сейчас реализованы проверки `PUT /api/v1/bonus/packets/refill` — выбора бонусного
пакета для пополнения:

- запрос с пустым заголовком Authorization;
- обязательные и дополнительные поля;
- допустимые и запрещённые статусы пополнения;
- некорректные типы и значения `refillId` и `bonusPacketId`;
- структура ошибок валидации и точный набор ошибок отсутствующих полей;
- запрос с токеном другого пользователя;
- сохранение пакетов MOSTBET и MWL в БД.

Регистрация пользователя через API, SSH и MySQL используются для подготовки
данных. Проверки регистрации как самостоятельного API пока не выделены.

## Технологии

| Инструмент | Назначение |
| --- | --- |
| Python | Язык тестов; в коде используется синтаксис Python 3.10+ |
| pytest | Запуск тестов, фикстуры и параметризация |
| pytest-xdist | Параллельное выполнение тестов в отдельных процессах |
| Pydantic | Проверка структуры и типов полей ответов об ошибках |
| HTTPX | HTTP-запросы к API |
| PyMySQL | Подготовка и проверка данных в MySQL |
| Fabric | Выполнение команд на стенде по SSH |
| python-dotenv | Загрузка настроек из `.env` |
| Allure | Отчёты, шаги и вложения HTTP-запросов и ответов |

Зависимости перечислены в `requirements.txt`. Для установки используйте
версию Python, совместимую с указанными версиями библиотек.

Сейчас модели импортируют Pydantic, но он ещё не указан в `requirements.txt`.
До обновления списка зависимостей его нужно установить отдельно:

```bash
python -m pip install "pydantic>=2,<3"
```

Для воспроизводимой установки добавьте проверенную версию Pydantic в
`requirements.txt`.

## Структура проекта

```text
.
├── src/
│   ├── config.py          # Настройки API, SSH и MySQL
│   ├── httpx_client.py    # HTTP-клиенты и вложения Allure
│   ├── one_click.py       # Регистрация и данные пользователя
│   ├── db_client.py       # Клиент MySQL
│   ├── ssh_client.py      # SSH-клиент и создание пополнения
│   └── models/
│       └── bonus_packets_models.py  # Pydantic-модели ответов об ошибках
├── tests/
│   └── bonus_packets/
│       └── test_api_bonus_packets_refill.py  # Интеграционные тесты бонусных пакетов
├── conftest.py            # Общие клиенты и фикстуры подготовки данных
├── pytest.ini             # Настройки pytest и Allure
├── requirements.txt       # Зависимости Python
└── .env.example           # Шаблон настроек окружения
```

Папки `allure-results/` и `allure-report/` создаются при запуске тестов
и генерации отчёта. Они исключены из Git.

## Установка

Выполняйте команды из корня проекта:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
```

Для Windows команда активации в PowerShell: `.venv\Scripts\Activate.ps1`.

## Настройка окружения

Заполните `.env` значениями тестового стенда:

| Переменная | Назначение |
| --- | --- |
| `DEV_STAND` | Имя стенда; адрес API: `https://<DEV_STAND>.dev-mst.com` |
| `SSH_HOST` | Суффикс SSH-хоста; итоговый адрес: `<DEV_STAND>.<SSH_HOST>` |
| `SSH_USER` | Пользователь SSH; текущий DB-клиент использует это же имя для MySQL |
| `HOST` | Адрес MySQL |
| `PORT` | Порт MySQL; укажите явно для своего окружения |
| `PASSWORD` | Пароль MySQL |
| `DATABASE` | Имя базы данных |

Файл `.env` исключён из Git. Не добавляйте реальные учётные данные в код
и `.env.example`.

Для текущих сценариев нужны:

- доступ к API и MySQL тестового стенда;
- SSH-доступ по ключу или через SSH-agent и право выполнять `sudo -iu mostbet`;
- команда `simulate:refill:greenback` в `/var/www/mostbet/current`;
- права на чтение таблиц тестируемого функционала и изменение статуса пополнения.

Для MOSTBET фикстура выбирает первый существующий пакет с ID меньше `50000`.
На стенде этот пакет должен подходить для тестового пользователя. MWL-сценарии
используют ID `50000` и `50001`. Для отсутствующего пакета выбирается свободный
ID из диапазона `49000–49999`.

Текущая подготовка данных предполагает, что `username`, полученный при
регистрации, соответствует `refill.user_id` и подходит для SSH-команды пополнения.

## Запуск тестов

Полный запуск всех файлов, соответствующих шаблону `test_*.py`:

```bash
python -m pytest -q
```

Тесты функциональной области или отдельного файла:

```bash
python -m pytest -q tests/bonus_packets
python -m pytest -q tests/bonus_packets/test_api_bonus_packets_refill.py
```

Один тест, включая все его параметры:

```bash
python -m pytest -q tests/bonus_packets/test_api_bonus_packets_refill.py::TestAPIBonusPacketRefill::test_negative_field_validations
```

Просмотр списка тестов без выполнения запросов:

```bash
python -m pytest --collect-only -q
```

Просмотр плана фикстур без их выполнения:

```bash
python -m pytest --setup-plan -q
```

Эти две команды не подтверждают работоспособность API и подготовки данных.
Зависимости Python должны быть установлены даже для сборки тестов.

Основной класс `TestAPIBonusPacketRefill` помечен маркером `integration`,
поскольку обращается к тестовому стенду. Маркер зарегистрирован в `pytest.ini`.

Запуск только интеграционных тестов:

```bash
python -m pytest -m integration -q
```

Запуск тестов без маркера `integration`:

```bash
python -m pytest -m "not integration" -q
```

Все текущие тесты относятся к интеграционному набору. Поэтому фильтр
`-m "not integration"` сейчас не выбирает тесты, и pytest завершается с кодом 5.
Отдельного набора без стенда и настроенного CI пока нет. При добавлении новых
тестов назначайте маркер всем сценариям с внешними обращениями: сам фильтр
не блокирует доступ к сети.

### Параллельный запуск

`pytest-xdist` включён в `requirements.txt`. Запуск основного набора
в двух рабочих процессах:

```bash
python -m pytest -m integration -n 2 -q
```

Каждый параметризованный случай выполняется как отдельный тест. Внутри теста
сохраняется порядок подготовки данных, запроса и проверок. У каждого рабочего
процесса свои HTTP-, SSH- и DB-клиенты: фикстуры уровня `session` и `module`
не разделяются между процессами.

Число после `-n` задаёт количество рабочих процессов. Начните с двух,
затем сравните время и стабильность при четырёх. Выбирайте минимальное число,
которое даёт почти лучшее время без дополнительных таймаутов и ошибок стенда.
Независимость пользователей и пополнений должна сохраняться для каждого случая.

## Ожидаемые результаты текущих сценариев

| Сценарий | Проверяемый результат |
| --- | --- |
| Пустой Authorization | HTTP 401, код `401`, сообщение `JWT Token not found` |
| Допустимый состав полей и разрешённый статус | HTTP 200 и `[]` |
| Отсутствие обязательных полей | HTTP 400, `VALIDATION`, `Validation failed`; точный набор и количество ошибок полей |
| Запрещённый статус пополнения | HTTP 422, `REFILL_STATUS_NOT_ALLOWED`, `refill_status_not_allowed` |
| Некорректный тип или значение refillId | HTTP 400, `INVALID_REQUEST`, `Invalid request`; структура ответа проверяется моделью Pydantic |
| Пополнение другого пользователя | HTTP 404, `NOT_FOUND`, `refill_not_found` |
| Некорректный тип или значение bonusPacketId | HTTP 400, `INVALID_REQUEST`, `Invalid request`; данные пополнения в обеих проверяемых таблицах не изменяются |
| Пакет MOSTBET | HTTP 200 и `[]`; наличие выбранного пакета в `user_selected_option`, три уникальных по имени записи в `refill_additional_data`, корректные ID и источник |
| Пакет MWL | HTTP 200 и `[]`; `user_selected_option` не изменяется, в `refill_additional_data` три уникальных по имени записи, корректные ID и источник |

В матрицах некорректного ввода используются значения из параметризации;
конкретный вариант отображается в названии теста. Проверка `true` сейчас
закомментирована и в прогон не входит. Отдельной проверки отсутствующего
положительного ID пакета в основном наборе сейчас нет, хотя фикстура
`missing_bonus_packet_id` сохранена.

### Модели ответов

Модели находятся в `src/models/bonus_packets_models.py`:

- `BonusPacketRefillErrorResponseBase`: обязательные непустые строки `id`,
  `code`, `message`;
- `ValidationErrorDetail`: обязательные непустые строки `key` и `fieldName`;
- `BonusPacketRefillErrorResponseDetails`: базовая ошибка и список `details`.

Включены строгая проверка типов и запрет дополнительных полей. Модели
используются в проверках отсутствующих обязательных полей, некорректного
`refillId` и `bonusPacketId`. Конкретные бизнес-значения проверяются отдельными `assert`.
Другие ответы пока проверяются напрямую, без моделей.

## Подготовка тестовых данных

Общие фикстуры находятся в `conftest.py`:

| Фикстура | Назначение |
| --- | --- |
| `httpx_client` | Общая HTTP-сессия с вложениями Allure |
| `bonus_packets_client` | Запросы API бонусных пакетов |
| `user_client` | Запросы регистрации и получения данных пользователя |
| `create_user` | Новый `User` с `username`, `password` и `jwt_header` |
| `create_user_and_refill` | Фабрика: `user, refill_id = create_user_and_refill(status)` |
| `database_client` | Подключение к MySQL на время тестового модуля |
| `ssh_client` | SSH-клиент на время тестового модуля |
| `valid_bonus_packet_id` | Существующий пакет MOSTBET |
| `missing_bonus_packet_id` | Отсутствующий ID пакета для негативного сценария |

Каждый вызов `create_user_and_refill(status)` регистрирует пользователя,
создаёт пополнение через SSH, ожидает появления записи в БД и устанавливает
статус `0`, `1`, `2` или `3`. Для запроса от владельца используйте
`user.jwt_header` из той же пары.

MySQL-клиент работает с `autocommit=True`, чтобы отдельные запросы чтения
видели зафиксированные изменения API и SSH.

Тесты создают пользователей и пополнения, изменяют статусы и выбранные пакеты.
Используйте выделенный тестовый стенд. Автоматическая очистка созданных
сущностей пока не реализована; очистка выполняется по правилам стенда.

## Отчёты Allure

Сбор результатов в `allure-results/` включён в `pytest.ini`. Для просмотра
HTML-отчёта отдельно установите Allure CLI и совместимую Java; команда `allure`
должна быть доступна в терминале.

Запуск с очисткой результатов предыдущего прогона:

```bash
python -m pytest -m integration --clean-alluredir
```

Генерация и открытие отчёта:

```bash
allure generate allure-results -o allure-report --clean
allure open allure-report
```

Отчёт можно сформировать и после падения тестов. Без `--clean-alluredir`
результаты разных запусков накапливаются. Для остановки сервера просмотра
нажмите Ctrl+C.

В отчёте доступны русские названия сценариев, параметры, шаги, HTTP-вложения
и ссылки на тест-кейсы TestRail. Ссылки задаются через `@allure.testcase`:
это переход к ручному кейсу, а не автоматическая отправка результатов в TestRail.
У параметризованного метода одна ссылка относится ко всем его вариантам.

Названия случаев задаются русскими `id` в `pytest.param` и подставляются
в `@allure.title` через `{param_id}`. В `pytest.ini` отключено экранирование
идентификаторов, чтобы кириллица читалась в выводе pytest. Общее описание
объясняет правило проверки и не перечисляет значения соседних случаев.
Запросы подготовки данных также проходят через общий HTTP-клиент:
перед передачей отчёта проверяйте вложения на наличие паролей и токенов.

## Добавление новых API и тестов

1. Добавьте методы запросов в соответствующий клиент в `src/`. Для новой
   функциональной области при необходимости создайте отдельный клиент,
   использующий общую HTTP-сессию.
2. Разместите тесты в `tests/<функциональная_область>/`. Имена файлов начинайте
   с `test_`, имена тестовых методов — с `test_`.
3. Общие фикстуры размещайте в корневом `conftest.py`, а специфичные для
   отдельной области — в её `conftest.py`, если он понадобится.
4. Подготавливайте независимые данные для сценариев. Для похожих проверок
   используйте `pytest.mark.parametrize` с понятными идентификаторами случаев.
5. В Allure сохраняйте общий `parent_suite` команды, указывайте функциональную
   область в `suite`, а метод и путь API — в `sub_suite`. В `title` называйте
   сценарий, в `description` — условия и ожидаемый результат, в `step` —
   фактически выполняемое действие или проверку. Для параметризованных названий
   используйте русские `id` и `{param_id}`. Общее описание должно быть верным
   для каждого отдельного случая и не перечислять соседние варианты.
   Добавляйте ссылку TestRail через `@allure.testcase`, сохраняя соответствие
   между ручным кейсом и автоматизированными сценариями.
6. Модели новых ответов размещайте в `src/models/`. В негативных запросах
   сохраняйте возможность передать некорректные типы и значения.
7. Проверяйте HTTP-статус, содержимое ответа и, когда этого требует сценарий,
   изменения данных. Для негативных сценариев учитывайте отсутствие
   нежелательных изменений.
8. Помечайте тесты, обращающиеся к стенду, декоратором
   `@pytest.mark.integration` на уровне класса или отдельного теста.
   Для тестов, работающих без стенда, этот маркер не назначайте.
9. Обновляйте этот README при добавлении новой области API, настроек окружения
   или способа запуска.
